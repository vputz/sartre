## Context

`publish(coord, files)` requires a source for every file. Changing one file in a multi-file artifact means re-supplying the whole tree even though the unchanged blobs are already stored, and a limited full-replacement republish silently orphans the complete corpus. A base version's `Snapshot.entries` already carry `(path, content_hash, size, inline)` for every file, so a derived publish can reuse unchanged entries by hash and only take sources for changed paths — producing a complete, self-describing version. Design reviewed with a prospective client; their two additions (report inherited-vs-replaced; guard a non-head base) and the verify-ordering concern shaped the final scope.

## Goals / Non-Goals

**Goals:** derive a new version from a base changing only some paths; never need the bytes of unchanged files; identical lease/commit/CAS safety and provenance as `publish`; report what landed; a verify-before-promote path.

**Non-Goals:** no in-place mutation (always a new immutable version); no diff/patch encoding (self-describing full manifest); no change to `publish`; **pointer deletion + the race-safe staging cleanup are a sibling change** (`pointer-deletion`), not this one.

## Decisions

- **A separate method `publish_over`, not a `base=` flag on `publish`** — keeps `publish`'s full-replacement contract crisp. It is "publish-with-a-base," resolving inheritance at publish time into a *complete* manifest (not a diff), so every version stays self-describing; there is no server, so the base manifest is read client-side via `resolve` (entries + hashes only, no blob bytes).
- **`base: Ref = HEAD`.** Default to the current head — the common "patch the latest" case. Read-only; the base is never modified.
- **Apply order `remove` → `rename` → `changes`, then reuse the rest by hash.** `rename` is a pure manifest re-key: move the base entry (its `content_hash`/`size`/`inline`) to the new path, drop the old — **no source, no upload**. `changes` sources are hashed (pass 1) into fresh entries. `manifest_version` over the merged set gives the new version, so a no-op derive, or an identical-bytes override, yields the base's own id (content-addressed identity — good Hypothesis properties). Removing/renaming an absent path raises `PathError`.
- **Lease over ALL hashes, upload only `changes`.** The lease covers every hash in the new manifest (changed + inherited), so an inherited blob is a GC root from before upload through commit and advance — publish's exact protection over a different entry set (the blob/lease safety needs no new modelling). Reused and renamed entries touch zero blobs.
- **The advance is CAS'd against the BASE version, not a freshly-read head — and this needs TLA.** `_write_version` currently reads `start = head(pointer)` at write time and uses it as the CAS `expected`. That is correct for `publish` (full replacement — advancing from whatever's current is intended) but **wrong for a derive**: the base is resolved at one instant and the advance reads the pointer at a later instant, so a concurrent `publish` that moved the pointer in between would let the CAS silently succeed while the derived content is stale — a lost update. This interleaving is *not* covered by the existing "two writers, same expected, one wins" result, so it gets its own model, `model/PublishOver.tla`. The fix (to verify): `_write_version` takes `expected` from the caller; `publish_over` passes the **base version** for a same-lineage advance (so a moved pointer → `Conflict` → re-derive), `None` for a fresh `--stage` pointer, the pointer's current value for a cross-lineage `--point`, and (only under `--force`) the current head for a deliberate divergent rollback. `publish` keeps passing head-at-write. The model checks the invariant *a pointer is never advanced to a version whose base differs from the pointer's value at advance*. **Verified** (`model/PublishOver.tla`): the base-version config passes non-vacuously; the fresh-head config produces the lost-update counterexample (derive reads base v0, concurrent publishes move head to v4, the advance overwrites it). So `publish_over`'s advance uses base-version `expected`. The same invariant applies to the separate promote of a `--stage`d version (moving head to a version derived from B must CAS against B); since `sartre point` operates on version ids and doesn't know a version's base, `--stage` records `derived_from` in the staged version's metadata, and the **base-aware safe-promote lands with the sibling verify-staging change** — until then the recommended flow is re-derive if head moved.
- **Return `PublishOverResult(version, inherited, replaced, added, removed, renamed)`** (a small frozen dataclass, precedent: `GCResult`) — the honest home for the counts the CLI reports. Slightly richer than `publish`'s bare `Version`; accepted.
- **Factor the shared tail.** `_write_version(coord, entries, uploads, *, pointer, metadata, actor, reason)` holds the lease → upload-the-given-sources → self-check → commit → self-check → CAS advance → release. `publish` passes every path as an upload; `publish_over` passes only `changes`. Already done in the base implementation.
- **Head-based divergence guard (CLI).** Refuse when the resolved `--from` base ≠ the coordinate's current **head**, unless `--force`. Keying on *head* (not the advanced pointer) is deliberate: it must permit `--stage` (derive from head, land on a staging pointer — base *is* head) and the normal patch, while catching the real footgun (`--from @old` while head moved on). The library stays unopinionated (base + pointer explicit, for deliberate rollback-patch); the guard lives only in the CLI.
- **`--force` states the damage.** On a divergent base, `--force` alone is insufficient: it also requires `-m/--message` and prints the discard summary (versions/paths in head but not in the derived version) before writing — a stated, visible act, important for last-copy-data archives.
- **`--stage` lands off head.** Generates a unique pointer name `staging-<hex>` (a valid alias segment — no `/`), advances that instead of head, and prints it, so the workflow is *derive → verify the staging ref → advance head separately*. The version is a pointer target, so it is retained + lease-safe during verification (no orphan-blob GC risk that a pointer-less commit would have across separate CLI invocations). Cleaning up a spent staging pointer needs `delete_pointer` — the sibling change — so `--stage`'s help notes it ships ahead of deletion.

## Risks / Trade-offs

- **Staging pointers accumulate until `pointer-deletion` lands** → accepted for now; unique names prevent collisions, and the sibling change adds cleanup. Documented in `--stage` help.
- **Reused-blob-missing edge case** (base out of retention, concurrently GC'd) → mitigated by lease-first over all hashes and the fact that `base` had to resolve; same shape as publishing against a non-retained base. Documented.
- **`--stage → verify → promote` lost update** → the direct advance is closed by base-version `expected`, but the separate promote (`sartre point head @staged`) advances head from *its* current value, not the staged version's base — so if head moved during verification, a naive promote could still drop it. The model probes this; the resolution (record the derived version's base and have the safe promote CAS against it, vs. document re-derive, vs. defer a `promote` verb to the sibling change) is decided by what the model shows, before §4 lands.
- **`PublishOverResult` vs `publish`'s `Version` return** → minor asymmetry; `.version` is the id, precedent set by `GCResult`.

## Migration Plan

Purely additive — new method, result type, and CLI command; no data/schema/existing-API change. Rollback is dropping them.
