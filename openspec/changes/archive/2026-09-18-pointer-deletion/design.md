## Context

`publish-over --stage` shipped ahead of its two dependencies (recorded in that change's design as a sibling): a way to remove the throwaway `staging-<hex>` pointer, and a base-aware safe promote. The Registry has never had pointer deletion — `set_pointer` only advances. The four backends store pointers very differently: memory a `dict[str, Version]` under a lock; SQL a `pointers` row with a conditional `DELETE`; S3 an **append-only per-pointer event stream** with put-if-absent as the only write primitive and no row to delete at all. `PointerMove.to_version` is a non-optional `Version` and `pointer_moves.to_version` is `NOT NULL`, so "moved to nothing" cannot be recorded today. `S3Drop.tla` proves the *version*-tombstone discipline (tombstone-before-delete + resolve-skips-tombstoned) but is keyed by manifest hash, not by pointer/event — pointer deletion is a distinct interleaving.

## Goals / Non-Goals

**Goals:** a compare-and-swap `delete_pointer` on the port + all four backends; a base-CAS `promote` that cannot lose a concurrent publish; `--stage` records `derived_from` so promote has a base to check; pointer deletions retained in the forever history; the S3 pointer-drop race modeled and verified.

**Non-Goals:** no cascading version/blob GC on delete (retention GC still owns reclamation); no whole-coordinate deletion; no change to `publish`/`publish_over` beyond `--stage` writing `derived_from`; no permanent pointer locking (a tombstoned pointer name can be re-created).

## Decisions

- **`delete_pointer(coord, name, *, expected, actor, reason)` is a first-class Registry method, CAS on `expected`.** Symmetric with `set_pointer`: the same `expected`/`Conflict` contract, the same single appended `PointerMove`. Deleting an absent pointer with `expected=None` is a no-op (idempotent cleanup — a spent staging pointer deleted twice must not error). The facade — not the port — refuses `head`: the port stays mechanism, the facade owns the policy (head is a coordinate's identity).
- **`PointerMove.to_version: Version | None`, None = deletion.** The honest encoding, keeping "history is forever" whole. SQL `pointer_moves.to_version` is relaxed to nullable via an idempotent migration (add-column-shaped: detect the constraint, rebuild the table for SQLite / `ALTER COLUMN DROP NOT NULL` for Postgres). `from_version` keeps the prior value so a deletion is a legible audit row. Consumers reading history must tolerate `None` — called out as a (minor) type change in the proposal Impact.
- **S3 deletion is an append-only tombstone *event*, not a row removal.** A sentinel event appended at `seq+1` through the existing `_put_if_absent` gap-free CAS. `_pointer_scan` gains a notion of "tail is a tombstone → effective value is unset". `resolve`/`head` raise `NotFound`, `list_pointers` omits it; `list_log`/`list_pointer_history` retain it. Because it is just another event, a later advance appended after it re-creates the pointer — a tombstone is a tail *state*, not a lock. This mirrors the version-tombstone skip pattern but at the pointer/event layer, so it needs its own model.
- **Base-CAS `promote(coord, staged, *, pointer="head", …)`.** The `--stage`→verify→promote lost-update hole (design of publish-over, Risks): plain `point` CASes head against its *current* value, so a publish during verification is dropped. `promote` instead reads the staged version's `derived_from` (the base it was derived from) and CASes `pointer` against that — identical discipline to `publish_over`'s same-lineage advance, so a moved head → `Conflict`. This is why `--stage` must now write `derived_from`. Absent `derived_from` (hand-made alias, pre-feature stage) → refuse rather than silently last-writer-win; a `--force` flag drops to plain `point` for the deliberate case.
- **`--stage` records `derived_from=<base version>` in the staged version's metadata.** `publish_over` already threads `metadata` through to `commit`; the CLI `--stage` path injects `derived_from` into it. It lives in the version metadata (shared, immutable, self-describing) rather than the pointer event, because it is a property of the derived *version*, and `promote` resolves the staged ref to a version before reading it.
- **CLI: dedicated `delete-pointer` and `promote` commands** (chosen over folding `--delete` into `point`). `delete-pointer <coord:alias>` parses via `refs.parse_ref` + `pointer_name` and refuses `head`. `promote <coord[:pointer]> <staging|@version>` mirrors `point`'s arg shape, does the base-CAS advance, then deletes the spent staging alias on success. Both take `--as`/`-m`.
- **TLA `model/PointerDrop.tla` for the pointer-drop race.** Models `delete_pointer` (append tombstone at `seq+1`) racing a concurrent `set_pointer` re-creating/advancing the same pointer. Invariant: a reader never resolves a deleted pointer to a stale value, and delete+concurrent-recreate resolves to exactly one coherent tail outcome (the CAS/sequence winner), never torn. Two toggles establish each half is load-bearing (echoing `S3Drop_bad_noskip` / `S3Drop_bad_order`): `SkipTombstonedTail` (resolve honours a tombstone tail) and `TombstoneIsCasEvent` (the tombstone goes through the gap-free `seq+1` CAS rather than an unconditional write). **Verified** (`tla-verifier`): the ok config (both TRUE) holds `Safe` non-vacuously — 13 distinct states, depth 6, all five actions firing including delete-then-`Recreate`; `bad_noskip` (skip FALSE) breaks with a tombstone tail read through to the stale value below it; `bad_order` (CAS-event FALSE) breaks with an out-of-band tombstone diverging from the append-only order. So the S3 path skips a tombstone tail and lands the tombstone through the same `seq+1` CAS.

## Risks / Trade-offs

- **`PointerMove.to_version` widening is a public type change** → mitigated: additive at runtime (existing rows never null), and history consumers in-tree (CLI `history`, ops) updated; documented in Impact.
- **SQL migration on open** → must be idempotent and safe on a live DB; SQLite has no `DROP NOT NULL`, so the migration rebuilds the `pointer_moves` table (create-new → copy → swap) guarded by a constraint check, exercised by the persistent-backend equivalence tests.
- **Re-creatable tombstoned pointer** → a deleted staging name could be reused by a later advance; acceptable (names are unique-by-construction and deletion is for cleanup, not locking), and the model confirms delete+recreate stays coherent.
- **`promote` refusing on absent `derived_from`** → slightly more friction for hand-made aliases, but avoids silently reintroducing the very lost-update this change exists to close; the `--force` last-writer path remains for the deliberate case.

## Migration Plan

Additive API (`delete_pointer`, `promote`, async wrappers) + a widened `PointerMove.to_version` + an idempotent nullable-column migration on registry open. No data rewrite beyond the column relax; rollback is dropping the new methods (the nullable column is backward-compatible with the old `NOT NULL` code path as long as no null rows exist).
